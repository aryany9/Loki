## ADDED Requirements

### Requirement: LLM-driven response generation for tool observations
`ConversationSession` SHALL route terminal tool execution results and tool errors to the LLM for natural language response generation rather than substituting hardcoded language strings. Hardcoded fast-path string formatting (`formatFastPathResponse`) and static English error responses (`formatErrorResponse`) SHALL be retired so that tool outputs, errors, and missing items are synthesized into natural conversational responses matching the user's spoken or written language under a response-only constraint (supporting LiteRT regex `ResponseFormat.regex` and GBNF engines). Advancing tools that require further user input or tool execution (such as `lookup_contact`) SHALL retain their scoped tool grammar.

#### Scenario: Successful terminal tool execution synthesized by LLM in active language
- **WHEN** a terminal tool (e.g. `open_app`, `get_current_time`, `set_timer`, `call_contact`) executes successfully during a conversation turn
- **AND** the user spoke or wrote in a non-English language (e.g., Hindi or Spanish)
- **THEN** `ConversationSession` feeds the structured tool data to the LLM under a response-only constraint
- **AND** the LLM generates the spoken response in that language
- **AND** hardcoded English fast-path strings are bypassed

#### Scenario: Advancing tool execution retains tool grammar
- **WHEN** an advancing tool (`lookup_contact`) executes during a conversation turn
- **THEN** `ConversationSession` does NOT enforce response-only grammar on the next iteration
- **AND** the LLM is permitted to emit `ask_user` or `call_contact` under scoped tool grammar

#### Scenario: Tool execution error or not-found synthesized by LLM in active language
- **WHEN** a tool execution fails with an error or not-found result (e.g., `ToolErrorCode.NOT_FOUND`)
- **AND** the user spoke or wrote in a non-English language
- **THEN** `ConversationSession` feeds the structured error observation to the LLM under a response-only constraint
- **AND** the LLM generates the explanation in that language rather than speaking hardcoded English error text

### Requirement: LLM-driven response generation for permission rationales
When `ConversationSession` encounters `ToolExecutionResult.PermissionRequired`, it SHALL feed the structured permission requirement to the LLM under a response-only constraint to synthesize the user-facing permission request in the user's active language. In `AssistantSession`, this synthesized rationale SHALL be spoken before opening the permissions screen.

#### Scenario: Missing permission synthesized in user's language
- **WHEN** a tool execution requires a missing runtime permission
- **AND** the user spoke or wrote in a non-English language (e.g. Hindi)
- **THEN** `ConversationSession` prompts the LLM to explain the needed permission in the active language
- **AND** `AssistantSession` speaks the synthesized rationale before navigating to the permission screen

---

### Requirement: Multilingual voice confirmation repeat-back retention
When `ConversationSession` handles a confirmation question generated by the LLM for a pending action, it SHALL update `pendingVoiceConfirmation.repeatBack` with the LLM's generated question text so that silence timeouts and repeat prompts in `AssistantSession` speak in the user's language rather than reverting to a hardcoded English string.

#### Scenario: Voice confirmation retry speaks user's language
- **WHEN** the LLM generates a localized confirmation question for an action
- **AND** `pendingVoiceConfirmation` is registered
- **THEN** `repeatBack` is set to the localized question
- **AND** any repeat or retry turn speaks the localized question text

---

### Requirement: Dynamic TTS voice script adaptation
`AndroidTtsEngine` SHALL inspect outgoing utterance text and dynamically configure the underlying `TextToSpeech` engine's language locale to match the text's script or language family when `conversationLanguage` is `"auto"`.

#### Scenario: Devanagari script utterance sets Hindi TTS
- **WHEN** the spoken response text contains Devanagari characters
- **AND** `conversationLanguage` is `"auto"`
- **THEN** `AndroidTtsEngine` sets the TTS language to `hi-IN`

#### Scenario: Non-Devanagari Unicode script utterance sets corresponding locale
- **WHEN** the spoken response text contains Arabic (`\u0600..\u06FF`), Cyrillic (`\u0400..\u04FF`), or CJK (`\u4E00..\u9FFF`) characters
- **AND** `conversationLanguage` is `"auto"`
- **THEN** `AndroidTtsEngine` sets the TTS language to the matching language locale

#### Scenario: Explicit conversationLanguage overrides script detection
- **WHEN** `conversationLanguage` is explicitly set to a BCP-47 tag (e.g. "es")
- **THEN** `AndroidTtsEngine` uses the configured locale for speech output regardless of text script
